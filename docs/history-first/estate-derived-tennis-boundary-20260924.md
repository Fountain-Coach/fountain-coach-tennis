# History-first reconstruction: estate-derived tennis operating boundary

## Capability and requested outcome

Transfer the reusable EstatePublisher operating discipline into the public tennis repository without importing
estate-only runtime authority or publication mechanics.

## Current authority and execution path

- Tennis application authority: `app/` and its Node/ESM tests.
- Estate projection input: `estate-landing/`; its publication authority remains the parent Fountain Coach
  EstatePublisher/EstateStore path.
- Current repository procedure: `.codex/skills/tennis-multi-user-webapp/SKILL.md`.
- Infrastructure witnesses, if later requested, belong to the secure-publishing/deployment boundary, not application
  source.

## Existing working path and evidence

The EstatePublisher and secure-publishing procedures establish typed operation resolution, explicit target/scope,
opaque SecretStore references, one active process, terminal receipts, read-back/digest/rollback, and separate
DNS/TLS/service witnesses. The estate publication procedure separately establishes Store-to-Store route publication,
native preview leases, and WebKit AX/VRT acceptance.

## Failure evidence

The tennis repository has no admitted native service-release adapter. Treating `git push`, a directory copy, a
generic static server, or direct SSH as deployment would repeat the prior almost-deployment failure mode. The tennis
application also does not own FountainStore or EstatePublisher runtime authority.

## Smallest missing seam

The smallest useful change is documentation and routing: encode transferable operational invariants in
`AGENTS.md` and the tennis skill, while explicitly stopping future live service deployment at the absent typed
adapter. WebKit acceptance is the appropriate user-facing web witness; estate preview lease rules apply only to the
estate projection.

## Reuse decision

Reuse EstatePublisher's effect separation, secret custody, receipt/read-back, rollback, and fail-closed principles.
Do not copy Store publication, Governance numbering, estate navigation, Reframe launch, or FountainStore requirements
into ordinary tennis application development.

## Finite acceptance proof

1. The tennis guide and skill distinguish application work, estate publication, service release, and infrastructure
   verification.
2. Portable operational invariants and WebKit acceptance are recorded.
3. Estate-only rules are explicitly fenced.
4. Existing application tests and privacy checks remain unchanged and pass.
5. The change is committed and pushed to `main`.

## Claim classification

Observed: EstatePublisher procedures and the tennis repository's current boundaries. Inferred: a future service
release requires a typed adapter not currently present. Unestablished: production tennis service deployment and live
WebKit acceptance in this repository.

## Stop condition

Stop after the boundary is documented and validated. Do not create a deployment adapter or mutate infrastructure
without a separately scoped request and an admitted native execution path.
